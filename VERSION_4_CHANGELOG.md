# TalentLens: Architecture Version 4 Changelog & Traceability Matrix

**Document Version**: 4.0  
**Date**: November 19, 2026  
**Status**: Formal Engineering Changelog  

---

## 1. Executive Summary of Changes from Version 3 to Version 4

Version 4 addresses all lingering security vulnerabilities, referential integrity gaps, mathematical scoring flaws, RAG authorization leakages, and infrastructure staging issues identified during the Version 3 technical review.

---

## 2. Itemized Changelog & Resolution Status

| # | V3 Architectural Issue | V4 Engineering Correction | Affected Documents | Resolution Status |
| :--- | :--- | :--- | :--- | :--- |
| **1** | **Incomplete RLS on `organizations`**: V3 lacked explicit `ENABLE/FORCE RLS` on `organizations`, exposing tenant metadata to unauthenticated enumeration. | Added `ENABLE/FORCE RLS` with strict `SELECT` (active members or public active meta), `UPDATE` (`ADMIN`+), and `DELETE` (`OWNER` only). | `DATABASE_SCHEMA.md`, `RLS_POLICY_MATRIX.md`, `ARCHITECTURE_DECISIONS.md` | **Fully Resolved in Design** (Awaiting DB test) |
| **2** | **Weak Active Org Context Enforcement**: V3 membership helper did not strictly verify that the requested organization matches `app.current_org_id` and that the user's role satisfies the required action. | Redesigned `fn_has_active_org_membership(org_id, required_role)` to verify: (1) `app.current_user_id` is set, (2) `app.current_org_id` equals `org_id`, (3) membership is active, and (4) user role satisfies required role level. | `DATABASE_SCHEMA.md`, `RLS_POLICY_MATRIX.md`, `ARCHITECTURE_DECISIONS.md` | **Fully Resolved in Design** (Awaiting DB test) |
| **3** | **Missing RBAC Role Differentiation**: V3 defined `OWNER`, `ADMIN`, `RECRUITER`, `VIEWER`, but RLS policies treated all active members identically. | Implemented role hierarchy matrix in PostgreSQL and API guards, distinguishing admin actions (invites, role changes) from recruiter actions (jobs, screenings) and viewer actions (read-only). | `RLS_POLICY_MATRIX.md`, `API_DESIGN.md`, `SYSTEM_DESIGN.md` | **Fully Resolved in Design** (Awaiting API test) |
| **4** | **Unrestricted Recruiter Application Updates**: V3 allowed recruiters to `UPDATE` application rows without column restrictions, permitting malicious or accidental mutation of candidate ID, job ID, or submitted resume ID. | Added trigger `trg_protect_application_identity` locking `candidate_id`, `job_id`, `submitted_resume_id`, and `applied_at` against mutation; updates restricted strictly to `status` and `rejection_reason`. | `DATABASE_SCHEMA.md`, `SYSTEM_DESIGN.md` | **Fully Resolved in Design** (Awaiting DB test) |
| **5** | **Candidate Application to Inactive Jobs**: V3 did not prevent candidates from submitting applications to draft, closed, or archived jobs. | Enforced trigger `trg_validate_job_application_submission` asserting target job `status = 'PUBLISHED'` at submission time. | `DATABASE_SCHEMA.md`, `SYSTEM_DESIGN.md`, `API_DESIGN.md` | **Fully Resolved in Design** (Awaiting DB test) |
| **6** | **Screening Result Referential Disconnect**: V3 used independent foreign keys, allowing a screening result to reference an application from Job A while attached to a screening run for Job B. | Designed composite foreign keys linking `(job_application_id, job_id, candidate_id, evaluated_resume_id)` to `job_applications` and `(screening_run_id, organization_id, job_id)` to `screening_runs`. | `DATABASE_SCHEMA.md`, `SYSTEM_DESIGN.md` | **Fully Resolved in Design** (Awaiting DB test) |
| **7** | **Incomplete Resume Immutability**: V3 only protected 3 resume columns, leaving original filename, text chunks, and metadata mutable after submission. | Implemented comprehensive trigger `trg_protect_submitted_resumes` using `IS DISTINCT FROM` protecting all document content, hashes, version numbers, sections, and skills once submitted. | `DATABASE_SCHEMA.md`, `SYSTEM_DESIGN.md` | **Fully Resolved in Design** (Awaiting DB test) |
| **8** | **Screening Snapshot Concurrency Race**: V3 did not prevent late result insertion after a screening run was marked `COMPLETED`. | Implemented database trigger blocking `INSERT`, `UPDATE`, or `DELETE` on `screening_results` if `screening_runs.status = 'COMPLETED'`. Screening finalization locks the run row (`SELECT FOR UPDATE`). | `DATABASE_SCHEMA.md`, `SYSTEM_DESIGN.md` | **Fully Resolved in Design** (Awaiting DB test) |
| **9** | **Audit Log Insertion Forgery**: V3 policy used `WITH CHECK (TRUE)`, permitting arbitrary actor ID or organization ID spoofing. | Implemented security-definer function `fn_record_audit_event(...)` that derives actor and organization strictly from verified session context. Revoked direct `INSERT/UPDATE/DELETE` from `talentlens_app`. | `DATABASE_SCHEMA.md`, `RLS_POLICY_MATRIX.md` | **Fully Resolved in Design** (Awaiting DB test) |
| **10** | **Recruiter RAG Vector Authorization Leak**: V3 assigned resume vectors to a single tenant/job, failing when a candidate submitted the same resume to multiple companies. | Redesigned Recruiter RAG pipeline: backend queries PostgreSQL for authorized `submitted_resume_id`s for that job, then passes exact ID whitelist to vector retrieval filter. Vectors are candidate-owned. | `SYSTEM_DESIGN.md`, `API_DESIGN.md` | **Fully Resolved in Design** (Awaiting RAG test) |
| **11** | **Sender Role Forgery in Chat Messages**: V3 allowed clients to insert chat messages with `sender_role = 'ASSISTANT'`, enabling prompt injection attacks. | Added check constraint and trigger enforcing that client-inserted messages must have `sender_role = 'USER'`. | `DATABASE_SCHEMA.md`, `SYSTEM_DESIGN.md` | **Fully Resolved in Design** (Awaiting DB test) |
| **12** | **Scoring Defect: Unestablished Skills Penalized**: V3 formula divided demonstrated skills by total required skills, penalizing candidates for unmentioned skills. | Refactored scoring engine: separates Demonstrated, Explicitly Absent, and Unestablished skills. Calculates Evidence Coverage ($C_{evidence}$) and Uncertainty ($U$). If $C_{evidence} < 0.30$, status is `INSUFFICIENT_EVIDENCE`. | `SYSTEM_DESIGN.md`, `API_DESIGN.md`, `ARCHITECTURE_DECISIONS.md` | **Fully Resolved in Design** (Awaiting scoring test) |
| **13** | **Experience Scoring Contradiction**: V3 required numeric score while permitting "Unverified". | Defined explicit experience evaluation: non-overlapping calendar month deduplication, distinct academic/internship weights, and explicit `UNVERIFIED` flag incrementing $U_{exp}$ without arbitrary zeroing. | `SYSTEM_DESIGN.md`, `API_DESIGN.md` | **Fully Resolved in Design** (Awaiting scoring test) |
| **14** | **Roadmap Inversion**: V3 introduced bulk screening in Phase 3 before candidate application submission and resume pinning in Phase 4. | Inverted roadmap phases: Phase 2 is Candidate & Resumes; Phase 3 is Jobs & Applications (with pinning); Phase 4 is Screening (building on pinned applications); Phase 5 is RAG. | `IMPLEMENTATION_ROADMAP.md` | **Fully Resolved in Roadmap** |
| **15** | **Unverified "100% Offline" Claim**: V3 claimed the entire platform was 100% offline without verifying external telemetry or package dependencies. | Corrected claim to "Local model inference without paid cloud API keys". Documented commands to pull models: `ollama pull nomic-embed-text`, `ollama pull qwen3:4b`. | `SYSTEM_DESIGN.md`, `IMPLEMENTATION_ROADMAP.md` | **Fully Resolved in Documentation** |
| **16** | **Frontend React Version Clarification**: Prior notes questioned React 18 vs 19. | Inspected `frontend/react-ts/package.json`: verified active dependencies are `react: ^18.3.1` and `vite: ^5.4.10`. Confirmed React 18 is preserved. | `ARCHITECTURE_AUDIT.md`, `IMPLEMENTATION_ROADMAP.md` | **Verified Ground Truth** |
